## 二、目标与范围（Scope）
- 目标：将 Prowlarr 搜索客户端、TMDB 客户端、标题解析器以及 Torznab XML 生成模块串联，实现完整的 Torznab 搜索服务流（含电影搜索）。
- 范围：
  - 实现 `/api/v1/torznab` 入口的 `t=search`、`t=tvsearch`、`t=movie` 处理逻辑。
  - 实现搜索请求的"多轮增强"：TMDB 别名增强（可选） -> 多轮 Prowlarr 搜索合并去重 -> 标题解析 -> XML 格式化。
  - 支持并发处理：对 Prowlarr 返回的大量搜索条目进行并行的异步解析。
  - 集成缓存机制：减少对 TMDB 的重复请求。
- 非范围：
  - 本任务不包含下载客户端（Sonarr）的自动化订阅逻辑，仅处理作为 Indexer 的响应逻辑。

## 三、设计与实施

### 3.1 技术方案

**编排流程（四阶段管道）**：

1. **请求接收与参数解析**（`TorznabEndpoint`）
   - 解析 Sonarr 查询参数，构建 `SearchQuery`
   - 如果提供了 `tmdbid`/`tvdbid`，跳到步骤 2a；否则跳到步骤 2b

2. **增强搜索词**（TMDB 集成）
   - 2a. 有外部 ID：通过 TMDB `/find` 解析 `tmdbid`，再调用 `TMDBClient.get_alternative_titles()` 获取中文别名列表
   - 2b. 无外部 ID：直接使用原始查询词
   - 2c. TMDB 别名结果做缓存（TTL 1 小时）

3. **发起搜索与并行解析**（Prowlarr + Parser）
   - 对“原始词 + 别名”进行多轮 `ProwlarrClient.search_async()` 并合并去重
   - 使用 `asyncio.gather()` 并行调用 `TitleParser.parse_title()`
   - 并发限制：建议 `asyncio.Semaphore(10)`

4. **格式化响应**（Torznab XML）
   - 将解析后的 `ParsedTitle` 列表传给 `TorznabXMLBuilder`
   - 生成符合 Torznab 规范的 XML 响应

**设计模式**：
- 采用 **Composite Pattern** 思想封装编排逻辑：创建一个 `OrchestrationService`
- **异步处理流**：使用异步客户端 + `asyncio.gather` 并行处理搜索与解析
- **查询增强**：当 Sonarr 传入 `rid` (TVRage), `imdbid` 或 `tmdbid` 时，先调用 TMDB 获取剧集别名，再向 Prowlarr 发起包含别名的加权搜索

### 3.3 输入输出契约

#### 输入结构（SearchQuery 模型）
```python
class SearchQuery(BaseModel):
    t: str                          # 操作类型：search | tvsearch | movie | caps
    q: str | None = None            # 搜索关键词（t=search 时必填）
    season: int | None = None       # 季号（t=tvsearch 时使用）
    ep: int | None = None           # 集号（t=tvsearch 时使用）
    tvdbid: int | None = None       # TVDB ID
    tmdbid: int | None = None       # TMDB ID（用于 TMDB 别名增强）
    rid: int | None = None          # TVRage ID
    imdbid: str | None = None       # IMDB ID
    limit: int = 100                # 返回结果限制
    offset: int = 0                 # 分页偏移
```

#### 输出结构
- **成功**：`(True, xml_string: str)` - 符合 Torznab 规范的 XML 字符串
- **失败**：`(False, error_message: str)` - 包含错误详情的描述

#### 内部数据流
1. `SearchQuery` → `OrchestrationService.search()`
2. → `ProwlarrClient.search()` → `list[dict]` (原始搜索结果)
3. → `TitleParser.parse_title()` → `ParsedTitle` (并行解析)
4. → `TorznabXMLBuilder.build()` → `str` (XML 字符串)

### 3.4 API 端点设计

#### Torznab API 端点
- **端点路径**：`GET /api/v1/torznab`
- **认证**：使用 API Key（通过配置系统管理，与 Sonarr 配置一致）
- **响应格式**：`application/xml` 或 `application/rss+xml`

#### 请求参数（Query Parameters）
| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `t` | string | 是 | 操作类型：`search` \| `tvsearch` \| `movie` \| `caps` |
| `q` | string | 条件 | 搜索关键词（t=search 时必填） |
| `season` | int | 否 | 季号（t=tvsearch 时使用） |
| `ep` | int | 否 | 集号（t=tvsearch 时使用） |
| `tmdbid` | int | 否 | TMDB ID（用于别名增强） |
| `tvdbid` | int | 否 | TVDB ID |
| `rid` | int | 否 | TVRage ID |
| `imdbid` | string | 否 | IMDB ID |
| `limit` | int | 否 | 返回结果限制，默认 100 |
| `offset` | int | 否 | 分页偏移，默认 0 |

## 四、业务规则（Business Rules）
1. **优先增强原则**：如果解析器能识别出比 Prowlarr 原始数据更准确的季集信息，则在 XML 中覆盖原始属性。
2. **容错重试**：如果 Prowlarr 搜索暂时不可用，应返回标准的 Torznab 错误 XML 而非崩溃。
3. **并发限制**：限制单次请求解析条目的最大并发数（默认 10），防止 CPU 尖峰。
4. **缓存策略**：TMDB 别名查询结果应缓存（建议 TTL 1 小时），减少重复请求。
5. **降级处理**：TMDB 调用失败时不影响主流程，降级为无增强搜索。
6. **多轮搜索**：别名搜索结果需与原始词结果合并去重，避免重复条目。

## 五、验收标准（Acceptance Criteria）

### 5.1 功能验收
1. ✅ **基础功能**：
   - `t=search` 请求能返回正确的 XML 响应
   - `t=tvsearch` 能正确解析 season/ep 参数并返回对应集数
   - `t=movie` 能返回正确的 XML 响应
   - `t=caps` 能返回正确的能力集（调用 B-07 的 caps 功能）

2. ✅ **字段完整性**：
   - XML 中的 `torznab:attr` 包含 `season`、`episode`、`tmdbid`
   - 保留 Prowlarr 原始的 `seeders`、`peers`、`size`、`pubDate` 字段
   - 标题解析后的增强字段（resolution、codec、source 等）正确映射

3. ✅ **TMDB 增强验证**：
   - 提供 `tmdbid` 时，能从 TMDB 获取别名并增强搜索
   - 提供 `tvdbid/imdbid/rid` 时能解析为 `tmdbid`
   - 别名匹配提升解析成功率 ≥ 20%（对比无增强）
   - TMDB 调用失败时自动降级，不影响主流程

4. ✅ **并发处理**：
   - 100 条搜索结果能在 2 秒内完成解析和 XML 生成
   - 并发数可通过配置调整（默认 10）
   - 单个解析失败不影响其他条目处理

5. ✅ **异常处理**：
   - Prowlarr 不可用返回标准错误 XML（HTTP 200，XML body 包含错误标签）
   - 参数验证失败返回 `error code="200"`
   - 所有异常不导致进程崩溃

### 5.2 性能验收
1. ✅ **响应时间**：
   - 单次请求（100 条结果）总处理时间 < 2s
   - Prowlarr 搜索耗时 < 1s（网络依赖，可配置超时）
   - 标题解析平均耗时 < 5ms/条

2. ✅ **代码质量**：
   - Black、Ruff 检查通过
   - 核心逻辑单元测试覆盖率 ≥ 70%
   - 类型注解完整（mypy 检查通过）

3. ✅ **文档更新**：
   - README 或 API 文档更新使用说明
   - TODO.md 标记任务完成

## 七、风险与对策
- **性能瓶颈**：解析大量条目时 CPU 压力大
  - 对策：限制并发数（Semaphore(10)），考虑引入 Redis 缓存解析结果
- **搜索词偏移**：Prowlarr 原始搜索词可能不准
  - 对策：依赖 TMDB 别名增强，提供日志便于调试搜索词
- **TMDB 限流**：频繁调用可能触发速率限制
  - 对策：实现缓存机制（TTL 1h），失败时自动降级
- **并发冲突**：高并发场景下资源竞争
  - 对策：使用连接池管理 HTTP 客户端，限制全局并发数
